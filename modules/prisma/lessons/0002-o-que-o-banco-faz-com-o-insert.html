O que o banco faz com o seu INSERT

Você escreveu os models. Agora a pergunta é o que acontece quando uma linha chega com dados faltando. A resposta explica por que o @default errado causa um bug sem nenhuma mensagem de erro.

Sua vitória de hoje Olhar para um INSERT e prever o resultado: a linha é gravada, o banco preenche algum valor ou o insert falha (e com qual erro). Depois, decidir com segurança quando um campo merece @default. Tempo: uns 12 minutos. A prática local é opcional e fica no fim.

Aquecimento

Matéria da lição 1. Responda de cabeça antes de abrir.

Qual é a diferença entre name String? e createdAt DateTime @default(now())?

O ? permite que a coluna fique sem valor (NULL). O @default faz o banco preencher um valor quando ninguém informa a coluna. Hoje você vai ver as duas regras funcionando dentro do banco.

1. Do contrato à tabela, em dois comandos

No Prisma 8, o caminho do arquivo até o banco é este:[Prisma]

PassoO que faz
prisma/contract.prismaVocê descreve os models.
npx prisma contract emitLê o contrato e gera contract.json e contract.d.ts, que são os tipos que o seu código TypeScript vai usar. Rode de novo a cada mudança no contrato.
npx prisma db initCria as tabelas no PostgreSQL (o CREATE TABLE da lição 1).

Depois disso, cada db.orm.public.Event.create({...}) do seu código vira um comando SQL INSERT. Quem decide se a linha entra ou não é o banco, e é isso que você vai aprender a prever.

2. As quatro regras do INSERT

Um INSERT lista as colunas que você está enviando e os valores delas:[PG]

INSERT INTO "Event" ("name", "theme", "minutes", "company")
VALUES ('Tech Day', 'Web', 90, 'Acme');

Repare que a coluna "date" não aparece. Para cada coluna que não foi enviada, o PostgreSQL faz isto:[PG]

  1. Tem DEFAULT? O banco usa o valor padrão. É assim que o id (autoincrement()) e o createdAt (now()) se preenchem sozinhos.
  2. Não tem default? A coluna fica NULL.
  3. Ficou NULL numa coluna NOT NULL (campo sem ?)? O insert inteiro falha com o erro 23502.[PG]

Depois disso, o banco aplica a quarta regra, que vale para todas as colunas:

  1. Valor repetido numa coluna @unique ou @id? O insert falha com o erro 23505.[PG] Esse é o mesmo código que o Prisma devolve em error.sqlState.[Prisma]

Quando um insert falha, nenhuma coluna é gravada. Não existe "gravou pela metade".

3. Experimente: o seu model Event

Abaixo estão duas versões do Event que você desenhou na lição 1. A única diferença está no campo date.

Antes de clicar, preveja. Desmarque a coluna date (o seu código "esqueceu" a data) e aperte INSERT nas duas versões. O que vai acontecer em cada uma?

Versão A: date DateTime @default(now())

Este é o seu rascunho original.

Versão B: date DateTime

Obrigatório e sem default.

Experimente também: aperte INSERT duas vezes seguidas com a mesma company, ou digite NULL em algum campo.

O bug silencioso

Na versão A, o evento é gravado com a data de hoje e o banco não reclama. Ninguém percebe até um usuário ver o "Tech Day" marcado para o dia errado. Na versão B, o erro 23502 aparece no momento em que o bug acontece, que é exatamente quando você quer descobrir.

Um @default não significa "o valor que costuma ser". Ele diz: "se ninguém informar, este valor está correto". Para a data de cadastro isso é verdade. Para a data de um evento, não é.

Regra prática Se o valor precisa vir do usuário, o campo fica obrigatório e sem default. Use @default só quando o banco realmente sabe o valor certo: id, createdAt ou um estado inicial como @default("draft").

Repare nos ids. Depois de um insert que falhou, o próximo id pula um número. O banco tira o próximo valor da sequência antes de checar as regras, e esse valor nunca é devolvido.[PG] Buracos no id são normais: nunca use o id para contar linhas.

Pratique: quiz

Responda sem rolar para cima.

1. Na versão B (date DateTime, sem default), um insert que não envia "date"…

  1. grava a data atual
  2. grava NULL na coluna
  3. falha com erro 23502
  4. falha com erro 23505
Sem default, a coluna ficaria NULL, mas ela é NOT NULL (campo sem ?). Por isso o insert falha com 23502, o erro de valor nulo.

2. A sua Company tem cpf String? @unique. Um insert que não envia "cpf"…

  1. grava NULL no cpf
  2. grava texto vazio nele
  3. falha com erro 23502
  4. gera um cpf aleatório
Não há default, então a coluna fica NULL. Como o campo tem ?, NULL é permitido e a linha entra. Texto vazio ('') é um valor, não é ausência de valor.

3. Já existe um evento com company = 'Acme' e o campo é @unique. Um novo insert com 'Acme'…

  1. substitui o evento antigo
  2. grava duas linhas iguais
  3. falha com erro 23502
  4. falha com erro 23505
É uma violação de unicidade: erro 23505. O banco nunca substitui uma linha por conta própria. Atualizar é outro comando (UPDATE).

4. Num app de eventos, qual destes campos merece @default(now())?

  1. a data do evento
  2. a data de cadastro
  3. o nome do evento
  4. o tema do evento
A data de cadastro é, por definição, o instante do insert, então o banco sabe o valor certo. A data do evento só o usuário sabe.

5. Duas empresas sem CNPJ (cnpj NULL nas duas), com cnpj String? @unique. O segundo insert…

  1. falha por CNPJ repetido
  2. falha por NOT NULL
  3. grava, NULLs não colidem
  4. substitui a primeira empresa
Por padrão, o PostgreSQL considera que dois NULLs nunca são iguais, então uma coluna única aceita vários NULLs.[PG] Isso é bom (várias empresas sem CNPJ), mas mostra uma lacuna: nada impede uma empresa sem CNPJ e sem CPF. Vamos resolver isso numa lição futura.

Recupere da memória

Quais são as quatro regras do INSERT, em ordem?

(1) Coluna omitida com default recebe o default. (2) Sem default, recebe NULL. (3) NULL numa coluna NOT NULL gera o erro 23502. (4) Valor repetido numa coluna única ou na chave primária gera o erro 23505.

Por que @default no campo errado é pior do que um erro?

Porque o dado errado é gravado sem nenhum aviso. O erro aparece no momento do bug. O default errado só aparece quando alguém nota o dado errado, às vezes semanas depois.

2. Ganhar um PostgreSQL de graça

npx create-db@latest --env .env

Cria um banco temporário, sem cadastro, e grava a DATABASE_URL no arquivo .env. O banco é apagado em 24 horas, a não ser que você o reivindique pelo link exibido (é grátis).[Prisma] O .env já está no .gitignore: a URL tem a sua senha.

// use prisma-8

model Book {
  id         Int       @id @default(autoincrement())
  title      String
  isbn       String    @unique
  rating     Int?
  finishedAt DateTime?
  createdAt  DateTime  @default(now())
}

model Event {
  id      Int      @id @default(autoincrement())
  name    String
  date    DateTime
  theme   String
  minutes Int
  company String   @unique  // vamos melhorar isto na lição 3
}

4. Seu primeiro insert de verdade

index.ts

import "dotenv/config";
import postgres from "@prisma/orm-postgres/runtime";
import { contractFromJson } from "@prisma/orm-postgres/static";
import type { Contract } from "./prisma/contract.d";
import contractJson from "./prisma/contract.json" with { type: "json" };

const db = postgres({
  contract: contractFromJson<Contract>(contractJson),
  url: process.env["DATABASE_URL"]!,
});

async function main() {
  // Começa com a tabela vazia para você poder rodar várias vezes.
  await db.orm.public.Event.where({}).deleteAll();

  const event = await db.orm.public.Event.create({
    name: "Tech Day",
    date: new Date("2026-12-05T19:00:00-03:00"),
    theme: "Web",
    minutes: 90,
    company: "Acme",
  });
  console.log("Criado:", event);

  await db.close();
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
npx tsx index.ts

O id volta preenchido: foi o banco que gerou.[Prisma]
